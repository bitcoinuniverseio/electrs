# Bounded script output pages: draft source lane

Status: source only. The serving Electrs binary, native profile, legacy 500 UTXO cap, producers and consumers have not changed. This draft has controlled Windows tests for the production pager/helpers. The full Linux RocksDB/Indexer/Hyper integration is not yet compiled or qualified. Reorg/startup recovery remains withheld; this is not ready for native adoption or large-address parity acceptance.

The proposed separate read endpoint is `GET /v1/address/{address}/utxo-pages`. It requires singleton `network`, `profile_sha256` and full 40 character `artifact_revision` query fields. `cursor` is optional for the first page and authenticated for continuation. Missing build/source/bootstrap/coverage proof returns unavailable. Cross-scope or changed chain/mempool generation rejects continuation. The legacy `/address/{address}/utxo` route and its limits remain intact.

Every operation charges at most 500 logical record visits, including skipped history, confirmation, spending-edge, mempool and terminal seeks. It seeks the full encoded key exclusively; dense blocks and nested orphan confirmation scans resume through bounded pending state. A spent-heavy page may contain no outputs and still carry a continuation. Completion requires both script history and the qualified mempool terminal boundary. It never calls the legacy whole-address UTXO vector/cache helper.

The pager scans funding confirmations to EOF to choose the latest current transaction incarnation. Duplicate transaction IDs cannot be assumed absent: BIP30 permits fully-spent duplicates, and Mainnet contains historic overwrite exceptions. Earlier funding rows are not current outputs; a spend before the latest funding incarnation cannot consume the later coin. Conflicting current confirmations at the same height reject the contract. A funding/spending record without any confirmation proof is unknown and unavailable, never an inferred absence. See [BIP30](https://github.com/bitcoin/bips/blob/master/bip-0030.mediawiki).

Cursors retain the original creation/expiry clock (60 minutes), scope and pending position. The opaque payload is bounded hex plus HMAC-SHA256. Its key is 32 bytes from `/dev/urandom` at process startup, held only in memory; it is not an RPC credential, runtime-profile value, fixed fixture key or persisted/exported secret. Restart invalidates prior cursors. Cursor TTL is local operation lifecycle metadata, not a new chain observation.

URI, path and address bounds are enforced before address decoding. The new lane rejects duplicate/unknown query fields and bodies before the generic body collector. Its body receiver is dropped, with `Connection: close` on HTTP/1 rejection. Actual Hyper connection/HTTP2 stream behavior still requires isolated Linux integration tests. No URI/cursor is logged by the new route. Actual serialized responses are limited to 128 KiB; cursor is at most 8192 bytes, output total 100000 and logical work total 1000000.

At most 8 synchronous read owners are admitted. They retain their lease through actual database IO and final fences even if the caller disconnects. One fixed 10 second logical deadline spans snapshot/codec/page/serialization/final verification. Work returning after that deadline cannot publish a successful page. RocksDB 0.24 has no exposed IO-deadline cancellation API: a blocking call can finish late, and its lease stays held until it exits. No hard blocking-IO cancellation, detached worker, new listener or extra RPC pool is claimed.

The chain guard covers the existing writer's mutation interval across independent history/txstore stores and headers. Successful unchanged updates return before mutation and preserve the material epoch. Failed leases cannot be blessed by merely opening a later lease or observing the same tip. Added qualification point reads are fallible/bounded and added qualification locks use nonblocking reads; these failures withhold read proof without introducing new legacy producer exit errors.

This draft retains ordinary failed update phases, but no producer retry or deletion journal has been authorized/applied. A separate availability-only path may revalidate a pre-mutation storage fault at the existing loop boundary, using its already-read unchanged Core tip. It performs only bounded local reads, publishes a new token and never refreshes source observation time. Changed-tip indexing takes priority. Missing/mismatched metadata, poison and failed material phases cannot take this recovery path. A reorg has a separate completeness problem: legacy individual deletions swallow errors, and global spending-edge keys lack height/blockhash. Deleting an orphan duplicate spender can also erase an earlier current edge with the same key. Header validation of remaining records does not prove missing-edge absence. Reorg proof therefore remains withheld until exact recovery or an independently qualified index proof is implemented. Missing retained plans after panic and startup consistency also need explicit proof, without global scans or interference with valid indexing. Preexisting stores are unqualified by default, even after a later new or empty writer plan; only genuinely absent store paths can establish a fresh initial generation. This interim gate must be followed by a legitimate existing-dataset baseline/repair, not a restriction of the required datasets to fresh fixtures.

The final ready bootstrap response is captured from an existing `getblockchaininfo` request, by reference before the unchanged typed parser consumes the JSON. There is no additional RPC. Optional challenge metadata is bounded to 10000 decoded script bytes. Missing/malformed/wrong-chain metadata only makes the new lane unavailable; legacy startup behavior is preserved. Reconnect inherits this immutable bootstrap observation, which is labelled as not a current per-page Core proof.

The Signet commitment domain is explicit: SHA256 of lowercase script-hex UTF8. This matches existing qualified receipt convention (`22c3ce...` for default Signet); SHA256 of decoded script bytes is different (`e7ca5a...`). Neither is BIP325 magic derivation or signature verification. The independent backend current Core challenge/checkpoint guard remains required. Static profile hashing includes read-affecting configuration, feature/schema/build identity and the actual challenge commitment; raw private paths/addresses/cookies are not returned. Full source/build/serving provenance must be qualified externally; setting a full revision stamp alone is not integrity proof.

Required next gates: frozen source/lock/dependency binding, existing qualified Linux toolchain/resource isolation, actual temporary RocksDB writer/error/snapshot tests, actual Hyper body/disconnect tests, valid startup/reorg recovery proof, owner-approved safe native adoption, the large address acquisition bottleneck repair, then independently complete 12442-output parity. Controlled source tests do not promote any of the 632 required application rows or 39 protocols / 123 declared operations.
